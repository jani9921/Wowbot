## Implementation

1. `QuestModel.apply_quest_tool` grounds a literal healed/treated/revived
   objective in the exact special_item exported for its active quest. The
   original coarse API type stays in raw evidence; a contradictory LLM
   DEFEND hint cannot replace the grounded USE_ITEM_ON_TARGET action.
2. A uniquely matched, concrete, non-proxy TDB creature entry supplies a
   search candidate, not observed identity. The server must still contain
   that current non-removed GUID with a finite same-instance position.
3. `QuestObjectivePlanningMixin` reuses the shared MOVE/facing and friendly
   TARGET skills. It makes no input directly. Close acquisition uses the
   existing `TAB_FRIEND_RESCUE` activation as a shared friendly Ctrl+Tab
   primitive, whose result must exactly match the intended GUID/NPC ID.
   Three failed selections in 45 seconds suppress only that actor for the
   bounded window, allowing another known actor.
4. The existing item planner/UseItemSkill checks exact selected GUID, item,
   range, usability, cooldown and F7 recipient at dispatch. Unknown readiness
   does not authorize F7. Existing configured actionbar or revalidated
   visible inventory-button alternatives retain their original contracts.
5. Only UseItemSkill success through the specific QuestProgressVerifier
   retires a healed GUID for this session/objective (bounded 600 seconds,
   256 records). Click acknowledgement, cast start, cooldown, another
   objective's progress and failed use do not mean a successful heal.
6. Healing clauses are excluded from ordinary server kill-target entry
   acquisition. No unrelated combat/self-defence input policy is disabled.

No addon, bindings-cache, database, DLL or packet-capture backend changed.
This is not a new healing brain, scheduler or input owner.

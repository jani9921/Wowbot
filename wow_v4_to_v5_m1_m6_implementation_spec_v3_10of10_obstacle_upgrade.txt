============================================================
GLOBAL DATA CONTRACTS
============================================================

Use the project's language conventions. The pseudo-types below define
semantic contracts, not mandatory syntax.

------------------------------------------------------------
1. Timestamp
------------------------------------------------------------

All events/evidence/state updates MUST carry monotonic timestamps where
possible.

type TimestampMs = long

Rules:
- never compare wall clock for short-duration control logic if monotonic time exists
- store wall-clock only for logs/diagnostics
- stale evidence must be rejected based on age

------------------------------------------------------------
2. Confidence
------------------------------------------------------------

type Confidence = float  // range [0.0, 1.0]

Rules:
- uncertain perception outputs MUST include confidence
- deterministic events may use 1.0
- unknown confidence MUST NOT default to 1.0
- values outside [0,1] are invalid

------------------------------------------------------------
3. CorrelationId
------------------------------------------------------------

type CorrelationId = string/Guid

Every high-level attempt creates a correlation chain.

Example:
Skill attempt
→ input actions
→ resulting events
→ failure event
→ recovery
→ final SkillResult

All of these MUST be traceable through CorrelationId and/or ParentCorrelationId.

------------------------------------------------------------
4. WorldEntityId
------------------------------------------------------------

type WorldEntityId = stable runtime track id

This is NOT necessarily a WoW GUID.
For vision-first entities it is a temporal track identity.

============================================================
GLOBAL OWNERSHIP RULES
============================================================

GoalManager owns:
- active high-level goal
- goal priority
- goal lifecycle

Planner owns:
- decomposition of goal into domain-level intents/skills
- plan revision
- dependency ordering

Supervisor owns:
- which high-level runtime state currently runs
- preemption/arbitration
- safety/recovery precedence

WorldModel owns:
- canonical believed state
- never physical input

EventBus owns:
- event delivery only
- never domain state decisions
- never physical input

Perception owns:
- observations/evidence
- never keypresses

Navigation owns:
- movement planning and progress
- never combat ability choice

Combat owns:
- targeting and combat ability decisions
- asks Navigation for movement when required

Interaction owns:
- approach/face/hover/interact/verify flow
- uses Navigation for movement

Questing owns:
- quest/objective decomposition
- never reimplements movement/combat/interact

SkillExecutor owns:
- skill lifecycle
- timeout/retry/postcondition verification

InputController owns:
- physical input only
- no gameplay reasoning


============================================================
GLOBAL CONCURRENCY MODEL
============================================================

The implementation may use threads/tasks, but must preserve deterministic
ownership.

Recommended loops:

CaptureLoop:
    20–60 Hz depending on hardware

PerceptionLoop:
    adaptive, typically 10–30 Hz

WorldStateUpdateLoop:
    event-driven + bounded periodic reconciliation

SupervisorLoop:
    10–20 Hz

PlannerLoop:
    event-driven / goal changes / failures
    NOT every frame

NavigationControlLoop:
    10–20 Hz

CombatControlLoop:
    10–20 Hz or event-driven where appropriate

InputScheduler:
    serialized per client

Rules:
- only one subsystem may own continuous movement at a time
- InputScheduler must serialize conflicting key states
- no two systems independently hold W/A/S/D without arbitration
- long-running perception may not block input release
- cancellation token / cancellation context required for preemptible operations

Backpressure:
- EventBus queues MUST have bounded behavior
- low-value repeated events may coalesce
- critical events MUST NOT be silently dropped
- stale perception events may be discarded before processing

Critical events:
DEATH
DISCONNECT
COMBAT_STARTED
COMBAT_ENDED
STUCK_DETECTED
TARGET_DEAD
QUEST_COMPLETE
UI_FATAL_MODAL


============================================================
DEFAULT TIMING / THRESHOLD POLICY
============================================================

All numbers below are STARTING DEFAULTS, configuration values, not hardcoded
truth. They MUST be centralized in config.

Observation freshness:
- UI evidence stale after: 750 ms unless event-derived
- entity position stale after: 1000 ms
- target position stale after: 500 ms during combat
- minimap movement evidence stale after: 1000 ms
- world map region evidence stale after: 5000 ms

Interaction:
- hover stabilization: 120–250 ms
- interaction result wait: 1200 ms
- interaction direct retry budget: 3
- interaction reposition retry budget: 2

Combat:
- error-event correlation window after ability input: 1200 ms
- target reacquire timeout: 1500 ms
- target reacquire attempts: 2
- range recovery timeout: 3500 ms
- facing recovery timeout: 1800 ms
- LOS recovery timeout per attempt: 2500 ms
- LOS recovery attempts: 3

Navigation:
- possible stuck if progress score < 0.18 for 1500 ms
- hard stuck if progress score < 0.10 for 3000 ms
- progress recovered when score > 0.35 for at least 500 ms
- local replan budget before escalation: 2
- global replan budget: 1
- temporary failed-region TTL: 30–180 sec depending on failure

Entity tracking:
- tentative track confirmation: 2–3 consistent frames
- occlusion state after missing: ~250 ms
- LOST after missing: 1500–3000 ms depending on class/context
- immediate deletion prohibited

Confidence examples:
- high confidence: >= 0.85
- medium: 0.60–0.85
- low: 0.35–0.60
- insufficient: < 0.35

These values MUST be tuneable and logged when used.

------------------------------------------------------------
M1.9 PROGRESS SCORE
------------------------------------------------------------

Implement configurable weighted evidence.

Initial suggested formula:

ProgressScore =
0.30 * OpticalFlowProgress
+ 0.25 * MinimapDisplacementProgress
+ 0.20 * TargetDistanceImprovement
+ 0.15 * LandmarkParallaxProgress
+ 0.10 * MovementStateEvidence

Each component normalized [0,1].

If a component unavailable:
- renormalize remaining weights
- never substitute fake 1.0

Possible stuck:
score < 0.18 for >= 1500 ms

Hard stuck:
score < 0.10 for >= 3000 ms

Recovered:
score > 0.35 for >= 500 ms

Use hysteresis to avoid flip-flopping.

------------------------------------------------------------
M2.6 OUT OF RANGE RECOVERY
------------------------------------------------------------

State: RECOVER_RANGE

Entry conditions:
LastAbilityAttempt failed
FailureReason == OUT_OF_RANGE
Target still valid

OnEnter:
- pause offensive ability execution
- lock intended target id
- increment range recovery attempt
- request Navigation.ApproachTarget(
      targetId,
      desiredRange = clamp(ability.maxRange * 0.80, safeMin, safeMax)
  )

Tick:
If target lost:
→ RECOVER_TARGET

If target dead:
→ CONFIRM_KILL

If desired range belief reached:
→ Navigation.StopApproach
→ VERIFY_RANGE

Verification:
Either:
- distance belief valid
OR
- retry probe ability no longer produces OUT_OF_RANGE

Timeout default:
3500 ms

Budget:
2 direct approach attempts
then local replan
then target unreachable if still impossible

------------------------------------------------------------
M2.7 FACING RECOVERY
------------------------------------------------------------

State: RECOVER_FACING

Entry:
Failure == FACING_INVALID

Behavior:
- target bearing from WorldModel
- controlled turn toward target
- continuously reobserve
- stop when target center enters configured central cone

Initial central cone:
±15 degrees equivalent visual bearing

Timeout:
1800 ms

If bearing unavailable:
ActivePerception:
small camera/player orientation probe
reobserve

Never:
random full spin

------------------------------------------------------------
M2.8 LOS RECOVERY
------------------------------------------------------------

LOS is distinct from range.

State sequence:

RECOVER_LOS
→ SAMPLE_LOCAL_GEOMETRY
→ TRY_LATERAL_A
→ VERIFY
→ TRY_LATERAL_B
→ VERIFY
→ LOCAL_REPLAN
→ VERIFY
→ TARGET_UNREACHABLE

Lateral preference:
use free-space + target bearing.
Do not blindly hardcode left first every time.

Suggested offsets:
small lateral move equivalent 0.4–1.2 sec controlled movement,
but movement duration MUST be cut early when geometry/progress changes.

Budget:
3 recovery attempts total before escalation.

On repeated LOS fail:
TargetManager.Reachability penalty
DangerMap temporary obstacle entry
Planner may choose alternate target if allowed

- quest relevance still valid?

Do NOT treat obstacle detection primarily as an object-classification problem.

World3DObstacleSystem

List<DetectedObstacleClass>.

M4.8H MOTION-CONDITIONED OBSTACLE DETECTION
------------------------------------------------------------

This is a critical subsystem.

When the agent commands movement, compare expected visual motion with observed
visual motion.

Example:

Command:

Expected:
- ground optical flow consistent with forward translation
- landmark parallax
- minimap displacement if available
- target relative distance change where appropriate

Observed:
- near-zero translation-like optical flow
- minimap unchanged
- landmarks stable
- same frontal boundary persists

Then:
MotionMismatchConfidence increases.

This allows detection of:
- unknown collision geometry
- invisible/poorly classified blockers
- small props
- geometry missed by semantic detection

Motion mismatch MUST be direction-aware.

FORWARD command mismatch is not equivalent to:
TURN command mismatch.

M5.4A OBSTACLE/TRAVERSABILITY COUPLING
------------------------------------------------------------

The M5 Navigation stack MUST consume the M4 obstacle system as follows:

→ LocalMotionPlan
→ MovementController

→ MotionConsistencyMonitor
→ CollisionEvidence
→ LocalTraversabilityMap
→ ProgressMonitor / StuckClassifier

Local planner candidate scoring should include:

+ progress_toward_goal
+ traversability
+ corridor_alignment
- obstacle_cost
- danger_cost

- oscillation_penalty

select waypoint outside oscillation basin

WRONG_HEADING:
recenter heading
do not global replan immediately

DYNAMIC_BLOCK:
wait short bounded interval
or bypass

mark loop region penalty
rebuild corridor/global route
